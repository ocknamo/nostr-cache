# ストレージレイヤー設計仕様書

## 1. 概要
本設計書では、cache-relayのストレージレイヤーの実装仕様について記載する。
主にDexie.jsを使用したIndexedDBの実装とテストについて詳述する。

## 2. システム構成

### 2.1. 依存関係
#### 2.1.1. 主要依存パッケージ
- dexie: ^4.0.11（IndexedDBラッパーライブラリ）
- @nostr-cache/shared: ^0.1.0（共有型定義、共有ユーティリティ）

#### 2.1.2. テスト用依存パッケージ
- fake-indexeddb: ^6.0.0（IndexedDBモック）

### 2.2. 基本構成
- 実装ファイル: packages/cache-relay/src/storage/dexie-storage.ts
  （1 フィルタの読み方は packages/cache-relay/src/storage/dexie/query.ts）
- データベース: IndexedDB (Dexie.js)
- テーブル構成: events
  - 主要フィールド：id, pubkey, created_at, kind, tags, content, sig
  - インデックス用フィールド：indexed_tags
  - 検証状態フィールド：validated（0=未検証, 1=署名検証済み。boolean は
    IndexedDB でインデックス化できないため数値で保持）

### 2.3. インターフェース仕様
StorageAdapterインターフェースの実装
- saveEvent(event, options?): イベントの保存機能（`options.validated` で検証済みとして保存。省略時は未検証。既存行が検証済みの場合、再保存で未検証へ**ダウングレードしない**）
- getEvents(): フィルタに基づくイベント取得機能
- deleteEvent(): イベント削除機能
- clear(): ストレージクリア機能
- getUnvalidatedEvents(limit): 未検証イベントを保存時刻の古い順に取得（遅延検証の永続キュー。アクセス追跡しない）
- markValidated(ids): 検証済みフラグの一括付与（存在しない id は no-op）
- getValidationStatus(ids): id ごとの検証状態（`validated` / `pending` / `unknown`）を一括取得（主キー bulkGet。アクセス追跡しない）
- deleteEventsByIdsForPubkey(ids, pubkey): NIP-09 の `e` タグに対応する削除。`pubkey` が一致する行のみ削除し、kind 5 は削除しない（両方ともストレージ側で保証する）
- getCurrentVersion(address): 座標（kind / pubkey / `d` 値）に保存されている置換可能・アドレサブルイベントを取得。複数版があれば NIP-01 の順序（`created_at` の新しい方、同値は id の辞書順で小さい方）で 1 件を返す。リレーが「受信イベントを保存してよいか」の判定に使う書き込み経路の事前確認のため、アクセス追跡はしない。失敗は握り潰さず伝播させる（「未保存」と誤認すると古い版で新しい版を上書きしてしまうため）
- deleteEventsByAddress(address, until): NIP-09 の `a` タグに対応する削除。`created_at <= until` の版のみ削除。アドレサブル kind では `d` タグの一致を要求し、置換可能 kind では `identifier` を無視する（判定は cache-relay の共通純関数 `matchesAddressIdentifier`）

## 3. データベース設計

### 3.1. インデックス構成
#### 3.1.1. 単一フィールドインデックス
- id: プライマリキー
- pubkey: 著者検索用
- created_at: 時間範囲検索用
- kind: イベント種別検索用
- indexed_tags: タグ検索用（配列インデックス）

#### 3.1.2. 複合インデックス
- [pubkey+kind]: 著者とイベント種別の組み合わせ検索用
- [kind+created_at]: イベント種別と時間範囲の検索用。`limit` 付きフィルタを
  「その kind を新しい順に」走査して早期打ち切りする経路でも使う（4.1.0）
- [pubkey+created_at] / [pubkey+kind+created_at]: 著者を絞った時間範囲の検索用。
  `limit` 付きで著者が少数のフィルタを「その人の分だけ新しい順に」走査する経路でも使う（4.1.0）
- [validated+cached_at]: 遅延検証の永続キュー用。`validated=0` の等値プレフィックスで未検証イベントを `cached_at` 昇順（古い順）にスキャンできるため、FIFO バッチ処理に並び替えが不要

#### 3.1.3. 検証状態のインデックス戦略
- **id → 検証状態の参照**（クライアントのバッジ表示などで高頻度）は、`id` が主キーであるため **追加インデックス不要**。`bulkGet` による主キー直接参照が最速経路
- **未検証イベントのスキャン**（バックグラウンド検証）だけが `[validated+cached_at]` を使う
- 検証状態の読み取り（getValidationStatus / getUnvalidatedEvents）は LRU/LFU 用のアクセスメタデータを更新しない（ポーリングが退避順序を乱さないため）

### 3.2. タグインデックス仕様
- indexed_tagsフィールドの実装
- 優先タグの定義（e, p, a, t, d, h, m, q, r）
- タグインデックスの制限（最大100個）

## 4. 機能仕様

### 4.1. クエリ処理機能
- フィルタ条件に基づく最適なインデックス選択機能（`planQuery` / `buildOptimizedQuery`。
  下記 4.1.0 / 4.1.1）
- 複数フィルタの効率的な処理機能
- タグフィルタと時間範囲フィルタの組み合わせ処理

#### 4.1.0. 2 つのクエリプラン（`planQuery`）
フィルタごとに、読み方が 2 モードある。`planQuery` がどちらかを選び、
`queryEvents` がそのプランどおりに読んで切り詰める。

- **`scan`**（`buildOptimizedQuery`。4.1.1）: もっとも選択的なインデックスで絞り、
  返ってきた行を並べ替える。**一致した行**を全件読む必要がある
- **`newest`**: `created_at` を**降順**に走査する。NIP-01 の `limit` が求める順序
  そのものなので、`limit` 件そろった時点でカーソルを止められる。読むのは
  **走査した行**だけ

`newest` を選ぶのは `limit` があり、`ids` もインデックス可能なタグ条件も無いフィルタ。
どのカーソルを開くかは「そのフィルタが何本を要求するか」で決まる。

1. `authors` が少数（`MAX_ORDERED_AUTHOR_CURSORS` = 16 本まで。`kinds` 併記なら
   authors × kinds の本数で数える）→ **著者ごと**に `[pubkey+kind+created_at]`
   （`kinds` 無しなら `[pubkey+created_at]`）の降順レンジ
2. そうでなく `kinds` が少数（`MAX_ORDERED_KINDS` = 8 本まで）→ **kind ごと**に
   `[kind+created_at]` の降順レンジ。`authors` はインデックスに載せず、カーソルが
   1 行進むごとに `eventRowMatchesFilter` が判定する
3. どちらでもない → `created_at` を降順に走る

いずれの経路でも**判定に通った行だけが `limit` に数えられる**ので、この照合が
打ち切り条件そのものになる。

2 はフォロータイムライン（`<nostr-follow-timeline>`）のためにある。
`{kinds:[1],authors:[…500],limit:50}` は時間範囲を持たないので `scan` では
`[pubkey+kind]` の 500 本の部分範囲に載り、一致行を全件読む。実測（キャッシュ 5000 件・
一致 4000 件）で `getEvents` が 574ms、降順・早期打ち切りだと同じ答えが 36ms。

1 が要るのは、その裏返しが単著者タイムライン（`<nostr-timeline authors="npub1…">`）を
壊すため。`parseFilter` は必ず `limit` を入れるのでこの形も `newest` に載るが、
2 の経路に落とすと「その 1 人」を探して kind 1 を全部走査することになる。同じ
キャッシュでの実測で 128ms、同じフィルタを `scan`（`[pubkey+kind]`）で
引くと 8ms。著者ごとにカーソルを開けばその人の行しか読まない。

上限を 16 本にしているのは、サブレンジのシーク自体が高くつくため（`[pubkey+kind]` に
500 本積んだ `scan` が 538ms かかるのがまさにそれ）。「著者ごとに開くには多すぎ、
かつ一致が疎で `limit` が早く埋まらない」帯（17 人〜数百人でキャッシュにその人たちの
投稿がほとんど無い場合）は 2 の経路が `scan` より不利になりうるが、どちらも数十 ms の
領域なので、そこに合わせた調整はしていない。2 の最悪ケース（一致 0 件で kind 1 の
4000 行を走査）は実測 145ms で、既定の `storageMaxSize`（5000）が走査量の上限になる。
走査バジェットによる打ち切りは設けていない。

同着の扱いに注意がいる。IndexedDB の降順走査は `created_at` が同値のとき主キーの
**降順**で返すが、NIP-01（および `capEvents`）は **id 昇順**で切る。ちょうど `limit` 件で
止めると、残すべき小さい id の行を落としうる。そのため `readNewest` は境界の
`created_at` と同値の行を読み切ってから `capEvents` に渡す。打ち切り判定（`until`）は
`filter` より**先に**鎖へ積む。Dexie のフィルタ鎖は短絡評価なので、逆順にすると
一致しない行では打ち切り判定が評価されず、次の一致行まで走査が伸びる。

#### 4.1.1. インデックス選択の優先順位（`scan` モード）
インデックスは「1 つのキーに一致する行がどれだけ少ないか」の順に選ぶ。どの分岐でも
最終判定は `eventRowMatchesFilter` が行うので、変わるのは基本的に**答えを出すために
読む行数**だけである。

ただし `indexed_tags` 経由だけは結果も変わりうる。このインデックスは保存時に
100 件で切り詰められる（7 節）ので、単一文字タグが 100 個を超えるイベントは溢れた
タグでは引けない。全行走査してフルの `tags` 配列で照合していた経路（`kind` /
`pubkey` インデックス）と違い、**タグインデックスは取りこぼす**。`p` タグを 150 個
持つリプライが自分の `e` タグを落とす、というのがその形（優先タグ同士では相対順を
変えないため、`e` が後ろにあれば落ちる）。上流購読は開くので画面から消えるわけでは
ないが、キャッシュだけでは返らない。

1. `ids` → 主キー `id`。1 件につき 1 行で、これ以上絞れない
2. `authors` × 時間範囲、`authors` × `kinds` × 時間範囲 → `created_at`
3. `authors` × `kinds` → `[pubkey+kind]`。2 フィールドの等値で「その人のその kind」まで
   絞れる。アドレサブルの参照（`{kinds:[k],authors:[p],'#d':[識別子]}`）がこの形で、
   `d` の値は人をまたいで衝突する（`d:"1"` など）ため、タグより先に見る
4. 単一文字タグ条件（`#e` / `#p` / …）→ multiEntry の `indexed_tags`。
   `distinct()` を付ける（1 行が複数の指定値に一致しうる。root と parent の両方を
   `e` タグに持つ NIP-10 リプライがそれで、付けないと重複が `limit` を食う）。
   タグキーが複数ある（`{'#p':[X],'#e':[Y]}`）場合は**全キーの値の和集合**を
   `anyOf` に渡す。積集合の上位集合なので結果は正しいが、読む行数は
   「一番少ないキー」ではなく和集合ぶんになる
5. `kinds` / `authors` / 時間範囲の各単独・組み合わせ → `kind` / `pubkey` / `created_at`
6. どれも無ければ全件走査

タグ条件を単一フィールドの `kind` より先に見るのが要点で、`kind` インデックスは**その kind の全行**を
返す。`<nostr-post>` が 1 投稿につき投げる `{kinds:[1],'#e':[…]}`（リプライ、階層ごとに
1 本）と `{kinds:[7],'#e':[…]}`（リアクション）がまさにこの形なので、以前は投稿を開く
たびにキャッシュ内の全 kind 1 / 全 kind 7 を読み出していた。IndexedDB の読み出しと
`rowToEvent` はページのメインスレッドを使うため、同時に走っている投稿本体の
`{ids:[…]}` もその間は答えられない（5 万行のキャッシュで本文表示まで約 1.2 秒 →
約 0.08 秒）。

トレードオフ: 実装はどちらのキーが少ないかを問い合わせずに決めているので、これは
計測ではなくウィジェットが実際に投げる形に合わせた選択である。逆に振れる形が両側に
ある。

- 指定したタグ値に一致する行が、併記された `kinds` に一致する行より多い場合は
  タグを選んだのが不利になる（`{kinds:[30023],'#p':[有名人]}`）
- タグインデックスは `since` / `until` をインデックスで絞れず、期間外の行も読んで
  `eventRowMatchesFilter` で落とす（`{kinds:[1],'#t':[人気タグ],since:直近}`）。
  一方 `authors` と時間範囲を併記した形（`{authors:[p],'#e':[X],since:…}`）は
  優先順位 2 に先に当たるので `created_at` を走査する

埋め込みの `filters` 属性は利用者が書く JSON なので、この形は外から来る。

- 無効なタグ形式の検証と除外

### 4.3. フィルタ処理機能
- since/untilパラメータによる時間範囲フィルタ（**両端とも境界を含む**（NIP-01）。Dexie の
  `between()` は既定で上限排他のため、時間範囲の絞り込みは `betweenCreatedAt()` に集約し、
  全分岐で包含指定にそろえている。ここで境界のイベントを落とすと、最終判定の
  `eventMatchesFilter`（包含）では復活できない）
- 複合条件での時間範囲フィルタ処理
- limitパラメータによる件数制限（**一致するイベントのうち最新 N 件を、新しい順で**（NIP-01）。
  Dexie の `Collection.limit()` は選ばれたインデックス順の先頭 N 件になり最新順にならないため、
  切り詰めは常に `capEvents`（`created_at` 降順・id 昇順タイブレーク）が行う。
  一致件数が limit 以下でも並び順の要件は変わらないため、常に整列する。
  limit はフィルタごとに適用し、複数フィルタの結果は id で重複排除する。
  limit は `normalizeLimit` で非負整数へ正規化してから使う。
  `limit` を持つフィルタは `newest` プラン（4.1.0）に載り、走査を N 件で打ち切る。
  複数 kind の場合は kind ごとに最新 N 件を取って束ねてから切る。全体の最新 N 件は
  各カーソルの最新 N 件の和集合に必ず含まれる（部分集合の中での順位は全体での順位以下）
  ため、これで厳密に一致する）
- タグ値の検証と正規化処理

## 7. 制限事項
- インデックス化されるタグの数は最大100個（**保存時に切り詰める**ので、100 個を超える
  単一文字タグを持つイベントは溢れたタグでは引けない。4.1.1 でタグ条件を優先して
  引くようにしたため、`kinds` / `authors` を併記したフィルタもこの上限の影響を受ける。
  上限を見直すには既存行の再インデックスが必要）
- シングルレターのタグのみがインデックス化される
- 複雑なタグフィルタリングはパフォーマンスに影響を与える可能性あり
